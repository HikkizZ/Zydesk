# ADR 0032 — Versionado y publicación

**Estado**: aceptada · 2026-10-05 · precisa a ADR 0012 (CHANGELOG por versión) y 0020 (etiquetas, imágenes en GHCR, CD por etiqueta: su regex pasa a admitir `-rc.N`) · recoge el punto 28 de ADR 0029 · se escribe en F9-T1, al inicio de la Fase 9 (`docs/specs/fase-9.md` §12 y §18.17)

## Contexto

Hasta la Fase 8b Zydesk no tuvo versiones: los cinco `package.json` (raíz, `apps/api`, `apps/web`, `apps/bot`, `packages/shared`) llevan `0.1.0`, no existe ninguna etiqueta git y `docs/CHANGELOG.md` acumula todo bajo `[Unreleased]`. La API ya publica `version` en `GET /api/salud` y en cada línea de log (ADR 0017), leyéndola de `apps/api/package.json` (`config/version.ts`); el bot hace lo mismo con `apps/bot/package.json`.

La Fase 9 (puesta en marcha) introduce el CD de ADR 0020: una etiqueta `v*` dispara el workflow que construye las imágenes, las publica en GHCR y, tras la aprobación del usuario, ejecuta `desplegar.sh` en el VPS con la etiqueta como único argumento. Desde ese momento la etiqueta es lo que viaja del repositorio a producción, el tag de las imágenes y lo que la salud de la API debe devolver: hace falta fijar qué es una versión, cómo se numera, dónde se escribe y quién la crea. El usuario decidió el 2026-10-05 (spec §0.1.3) que la salida de la fase sea la **v1.0.0** y que el correo entrante por IMAP quede para la **v1.1.0**; ADR 0029.28 dejó anotado que el esquema SemVer se registraría en una ADR de esta fase.

## Opciones consideradas

- **Una versión por workspace** (cada `package.json` con su propio número): lo normal en monorepos que publican paquetes en npm, pero Zydesk no publica nada (`private: true`), despliega las tres imágenes juntas y una sola etiqueta las nombra; versiones distintas por paquete obligarían a elegir cuál representa «la versión de Zydesk».
- **Herramientas de release** (`changesets`, `semantic-release`, `standard-version`): generan versión y CHANGELOG a partir de los commits; añaden dependencias y una convención de commits que el CHANGELOG escrito a mano por fase (ADR 0012) no necesita. Descartadas: la spec §2 fija «ninguna dependencia nueva».
- **Una sola versión para todo el monorepo, fijada con un script y escrita a mano en el CHANGELOG** (elegida): cero dependencias, un número, una etiqueta.

## Decisión

1. **Una sola versión para todo el monorepo.** La raíz y los cuatro workspaces llevan el **mismo** `version`. El script raíz `version:fijar` (`scripts/version-fijar.mjs`, sin dependencias) valida `X.Y.Z` o `X.Y.Z-rc.N` y escribe ese valor solo en los campos `version` de los cinco `package.json` y de `package-lock.json`, sin regenerar el lock (en Windows `npm` poda entradas opcionales) y sin crear commit ni etiqueta. Uso: `npm run version:fijar -- 1.0.0`. No se publica en npm (`private: true`). Nadie edita un `version` a mano.
2. **La versión que corre es la del `package.json`.** La API la expone en `/api/salud.version` y en cada log (ADR 0017), leída de `apps/api/package.json`; el bot, de `apps/bot/package.json`. Por eso el `version` debe ser **la etiqueta sin la `v`**: `desplegar.sh` comprueba, después de levantar, que la salud devuelve `"version":"<etiqueta sin v>"` y revierte si no (spec §5.5.11). Una imagen cuyo `package.json` no coincide con su etiqueta es un error de release, no una tolerancia.
3. **Etiquetas.** Formato `vMAJOR.MINOR.PATCH`, o prelanzamiento `vMAJOR.MINOR.PATCH-rc.N`; es lo único que acepta `desplegar.sh` (regex `^v[0-9]+\.[0-9]+\.[0-9]+(-rc\.[0-9]+)?$`, spec §3.2), lo único que cruza el SSH del CD y el tag de las imágenes en GHCR. Las etiquetas son **anotadas** (`git tag -a vX.Y.Z -m "Zydesk vX.Y.Z"`). Las definitivas solo apuntan a commits de `main`; las `-rc.N` existen para ensayar el despliegue completo (incluido el rollback) antes de la etiqueta definitiva y **pueden apuntar a la rama de la fase** (spec §18.2; precisa ADR 0020, cuya regex no las admitía). Una `rc` nunca se promueve renombrándola: la versión definitiva es una etiqueta nueva sobre `main`.
4. **Qué sube cada número (SemVer).** **MAJOR**: cambios incompatibles de datos o de API que exijan intervención al actualizar (migraciones destructivas, cambio del contrato entre la API y el bot, cambio de major de Postgres). **MINOR**: una fase o una funcionalidad nueva; **una fase = un MINOR** salvo decisión contraria. **PATCH**: correcciones sin funcionalidad nueva. Mientras una migración sea compatible con la versión anterior de la API (regla de `CLAUDE.md` que nace en esta fase, spec §9.2) actualizar y volver atrás no exigen intervención, y el cambio no es MAJOR.
5. **CHANGELOG por versión** (Keep a Changelog, ADR 0012). Cada PR escribe en `[Unreleased]`. Al cerrar una versión, `[Unreleased]` se renombra a `[X.Y.Z] - AAAA-MM-DD` y se agrega un `[Unreleased]` vacío arriba; al pie van los enlaces de comparación (`[X.Y.Z]: https://github.com/HikkizZ/Zydesk/releases/tag/vX.Y.Z`; desde la segunda versión, `compare/vA...vB`). Las secciones «Pendientes…» no se borran: se mueven a un apartado final «Pendientes conocidos» por versión. Durante la fase el encabezado `[1.0.0] - <fecha>` es **provisional**, marcado «(al cerrar)», y se fija el día de la etiqueta. Los prelanzamientos `-rc.N` no tienen sección propia en el CHANGELOG.
6. **Quién etiqueta y cuándo.** El usuario, **sobre `main` y después del merge** del PR de la fase, con confirmación explícita: el agente nunca hace `git push` ni crea etiquetas en el remoto sin pedirlo (`CLAUDE.md` §5). Secuencia (spec §9.2): mergear a `main` → `npm run version:fijar X.Y.Z` + CHANGELOG → commit `chore(release): vX.Y.Z` → `git tag -a vX.Y.Z -m "Zydesk vX.Y.Z"` → `git push origin main vX.Y.Z` → el workflow construye → el usuario aprueba el environment `produccion` → `desplegar.sh`. La `v1.0.0` se crea así al cerrar la Fase 9; durante la fase solo existen `v1.0.0-rc.N`.
7. **Imágenes.** Cada imagen (`zydesk-api`, `zydesk-web`, `zydesk-bot`) se publica con dos tags: `<etiqueta>` y `sha-<7 primeros caracteres del commit>`. **No existe `latest`**: un `latest` ambiguo contradice «lo que corre es una imagen trazable al commit» (ADR 0020) y permitiría que un `pull` sin versión cambiara producción sin pasar por una etiqueta.
8. **Release de GitHub opcional.** El workflow `desplegar.yml` **no** crea releases (mantiene `contents: read`; `contents: write` sería un permiso innecesario para un job que publica imágenes y despliega). Si el usuario quiere una release, la crea a mano en GitHub desde la etiqueta con el texto del CHANGELOG; si no, la etiqueta y el CHANGELOG bastan.
9. **Hoja de ruta inmediata.** **v1.0.0** = salida de la Fase 9 (puesta en marcha). **v1.1.0** = creación de tickets reenviando correos a una casilla (IMAP, ADR 0029.27), con su propia ADR; **no entra** en la Fase 9. Lo demás que se anotó para «después» (datos de la empresa en el PDF, Node 24 en runtime, Loki/Grafana) se asigna a una versión cuando se especifique, no aquí.

## Consecuencias

- Hay un único lugar donde cambia la versión (`version:fijar`) y un único artefacto que la nombra (la etiqueta); `/api/salud`, los logs, las imágenes en GHCR y `ZYDESK_VERSION` en el VPS dicen lo mismo, y `desplegar.sh` lo verifica.
- Un `rc` descubre los errores del CD antes de la etiqueta definitiva; el costo es que las `rc` apuntan a commits que después pueden no estar en `main` tal cual (el merge los reescribe o los agrupa). Se acepta porque la `rc` es un ensayo, no una versión publicada.
- Cerrar una versión es un commit `chore(release)` que toca cinco `package.json`, el lock y el CHANGELOG, siempre hecho por el usuario y nunca por CI; es un paso manual más, a cambio de no depender de herramientas de release ni de una convención de commits.
- Toda sección nueva del CHANGELOG nace en `[Unreleased]`; una fase sin entrada en `[Unreleased]` no puede cerrarse.
- ADR 0020 queda precisada en tres puntos: la regex de `desplegar.sh` admite `-rc.N`, las imágenes son tres (se suma `zydesk-bot`) y los tags son `<etiqueta>` y `sha-<7>` sin `latest`. El resto de las precisiones de la Fase 9 a ADR 0020 se registran en ADR 0031 al cerrar la fase.
- Si alguna vez un workspace necesitara publicarse en npm con su propio ciclo, esta ADR se sustituye; mientras Zydesk se despliegue como un todo, un número basta.
